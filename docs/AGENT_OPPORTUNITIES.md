# A4S Agent 机会评估与落地路线图

> 性质：产品与技术分析，不是已实现功能。
> 范围：当前 v0.2.0 代码（客户端/服务端拆分、空间协作、学习计划）与 8 条主业务链路。
> 日期：2026-11-26
> 口径：文中「现状」来自代码；「目标值」是待埋点校准的产品假设，不是实测结果。

---

## 0. 结论先行

1. **当前只有 1 个真 Agent**：学习计划（入口 `plan_agent`，v0.2.1 起内部为观察 / 规划 / 审核 / 写入四个有限角色，对外 6 步 + 5 个工具）。其余链路是「固定流水线 + 单次 LLM 调用 + 校验」。
2. **最值得做的不是「更多 Agent」，而是把 Agent 放进闭环的断点上。** 当前闭环断在三处：入库质量不可见、错题只收不治、计划只排不跟。
3. **建议只做 3 个亮点方向**：
   - **学习教练 Agent**：把一次性 7 天计划升级为「计划 → 执行 → 观察 → 重排」的长期回路。
   - **错题诊断 Agent**：从「收录错题」升级为「归因 → 3 分钟补漏 → 3 题验证 → 回写掌握度」。
   - **知识库体检 Agent**：入库后自动体检（未解析页、重复、主题错放、覆盖缺口），给报告并一键修复。
   - **当前优先级**：先做「教练 + 体检」两条链路；诊断作为后续可插拔的第三个 specialist，不阻塞前两者。
4. **不做的**：判分、检索召回、权限校验等确定性环节保持规则化；不做无人值守的「全自动学习」；不做通用聊天助手。
5. **竞争力不在模型，而在「本地全量学习数据 + 每一步可溯源 + 改动可撤销」**。这三条是通用 AI 学习产品短期抄不走的。

## 1. 现状：业务流程与 Agent 成熟度

### 1.1 Agent 成熟度分级

| 级别 | 定义 | 本项目现状 |
|---|---|---|
| L0 | 固定规则/固定流水线 | 入库、判分、定时、投稿审核 |
| L1 | 单次 LLM 生成 | 笔记起草、回顾分析 |
| L2 | 生成 + 校验/重试/阈值 | 问答、出题、引用白名单 |
| L3 | 受限工具循环（模型决定下一步） | **学习计划（唯一）** |
| L4 | 长期运行、主动观察与调整 | 无 |

### 1.2 主链路的真实实现

| 链路 | 用户入口 | 关键接口 | LLM 在哪 | 写死的步骤 | 失败/空数据 | 写入 |
|---|---|---|---|---|---|---|
| 资料入库/索引 | 知识库 → 上传/粘贴/网页 | `POST /api/documents/*` | 无（Embedding 除外） | 解析 → 切分 → 向量化 → FTS | 解析失败给原因；扫描 PDF 无 OCR → 0 片段 | `documents` `chunks` 向量/FTS |
| 问答 | 问答页 / 概览提问框 | `POST /api/chat`（SSE） | 命中/未命中各一次生成 | 检索 Top-K(5) → 阈值 0.42 → 拼上下文 → 生成 | 空库状态条；未命中先声明再通用知识补答 | 不落库（会话在前端） |
| 笔记 | 笔记 → 新建/从资料起草 | `/api/notes/*` | 起草一次 | 模板 → 生成 → 草稿 → 人工定稿 | AI 补写有标记；失败可重试 | `notes` |
| 出题 | 练习 → 选范围/题型/数量 | `POST /api/practice/generate` + 轮询 | 每种题型一次生成 | 取片段 → 按题型提示词 → 校验 → 组卷 | 材料不足直接拒绝；单次 ≤30 题 | `practice_sessions` `questions` |
| 作答判分 | 练习 → 作答 → 交卷 | `/sessions/{id}/start|submit` | 无（简答自评） | 客观题规则判分、多选全对才得分 | 断点续答；未答提醒 | `practice_sessions` `wrong_answers` |
| 错题本 | 错题本 | `/wrong-answers*` | 无 | 答错/自评未掌握自动收录，按题去重累加 | 按主题/资料/题型/时间筛选 | `wrong_answers` |
| 回顾报告 | 回顾 → 选 7/14/30 天 | `POST /api/reviews` | 一次生成三段分析 | 聚合数据 → 拼提示词 → Markdown | 空窗口出提示性报告 | `review_reports` |
| 学习计划 | 侧栏 Agent → 学习计划 | `POST /api/plan`（SSE） | 6 步循环内多次 | 模型选工具 → 执行 → 观察 → 再选 | 空库不出计划；工具失败换路 | `study_plans` |
| 定时邮件 | 设置/回顾 | APScheduler + SMTP | 无 | 每周固定 cron → 生成 → 发送 | 关机不补发；失败写原因 | `review_reports` + 推送状态 |
| 小组投稿 | 空间 → 上传/笔记 | `/api/spaces/*` | 无 | 待审 → owner 预览 → 批准/驳回 | 驳回带理由；审核前不索引 | 服务端 `documents`/`notes` |
| 共享/联邦选源 | 问答（有共享/组内库时） | `chat_service` 内 | 生成一次 | 本地 → 组内 → 联邦，来源上限 3 | 服务端离线显示离线；超时即过期 | 不落库 |

### 1.3 学习计划 Agent 的真实边界

- 文件：`backend/client/services/plan_agent.py`、`plan_tools.py`、`plan_prompts.py`、`backend/client/api/plan.py`。
- 工具：`get_progress`、`list_weak_points`、`list_wrong_answers`、`generate_practice`、`save_plan`。
- 约束：最多 6 步；只有 `save_plan` 写入；数字必须来自工具返回；`meta.steps` 保存每步入参与结果摘要；SSE 推 `step / thinking / plan / no_data / no_plan / error`。
- 现状：**一次会话出一份 7 天计划就结束**，没有执行跟踪、没有下一次重排、没有主动触发。

体检道（P2 已落地）是第二个：`client/services/agents/{inspector,fixer,health}.py` 只读巡检资料，Fixer 只出建议，Verifier 丢掉无依据提案；不调模型、不写业务表，运行账本与教练道共用。

### 1.4 已有的「类 Agent」防护（不要重复造）

- 引用编号白名单、答案归一化、JSON 容错重试（`llm_generator`）。
- 检索阈值 0.42 + 擦边命中追加判断提示（`retrieval` / `chat_service`）。
- 未命中两种分支：空库走页面状态条，有库未召回走回答上方声明。
- 多源选源：本地 → 组内 → 联邦，来源上限 3，文本层重排（`chat_service.py`）。
- 只读共享保护：`viewer` 除问答外写接口全部 403（`shared/api/deps.py`）。

### 1.5 基于代码事实的三个断点

1. **入库质量不可见**：解析器无 OCR、切分参数固定、主题/标签靠人；失败只有一句原因，用户不知道「这份 PDF 有多少页没解析出来」。
2. **学习闭环断在错题与计划之后**：错题本只做筛选与重练，不解释为什么错；计划只排一次，不跟踪执行。
3. **问答是单跳**：一个问句一次检索一次生成；多条件、多文档对比、需要澄清的问题会退化；引用白名单只能防编造编号，不能验证「引用是否真的支持结论」。

## 2. 候选场景全景（按优先级分三档）

> 评分口径见第 3 节。每个场景按「现状 → 痛点 → Agent 方案（能力/交互/触发）→ 价值」写。

### Tier A：核心亮点（建议做）

#### A1. 学习教练 Agent（升级现有计划）

- **现状**：`plan_agent` 一次生成 7 天计划；没有执行状态、没有 check-in、没有重排；历史计划只能看和删。
- **痛点**：计划是「一次性建议」。用户第二天没执行，系统不知道；下一周重新生成又是从零开始，无法体现「越用越懂你」。
- **Agent 方案**：
  - 能力：新增 `get_plan`、`update_plan_item`、`record_checkin`、`replan` 工具；模型根据完成率、错题变化、剩余天数决定「继续 / 压缩 / 改路线」。
  - 交互：计划卡片上直接勾选完成；「教练复盘」抽屉展示「为什么改」；每周一次主动复盘。
  - 触发：用户勾选/跳过任务、周结束时、连续两天未完成时。
- **价值**：把「排计划」从 30～60 分钟的一次性劳动，变成每周 5 分钟以内的对话；目标是把 7 天计划执行率提升 15 个百分点、次周留存提升 10%（待埋点校准）。

#### A2. 错题诊断与补救 Agent

- **现状**：答错自动进错题本，按题目去重累加次数；只能筛选、重练；没有归因、没有讲解、没有验证。
- **痛点**：错题本越积越多，用户不知道「是概念不懂、步骤错、还是粗心」；重练同一道题不等于补上知识点。
- **Agent 方案**：
  - 能力：错误归因（概念混淆 / 步骤缺失 / 计算粗心 / 审题偏差）+ 从资料里找 1～2 段依据 + 生成 1 段微讲解 + 3 道同知识点验证题 + 回写掌握度。
  - 交互：错题卡片上「诊断」按钮；诊断结果分「为什么错 / 3 分钟补漏 / 3 题验证」三段；验证通过打「已修复」。
  - 触发：新错题进入时异步预诊断；用户点开错题时展示。
- **价值**：单题人工翻资料 + 找题约 10～15 分钟，压缩到一次点击；目标是把同知识点二次错误率降低 20%、7 天内补救完成率达到 60%（待埋点校准）。

#### A3. 知识库体检 Agent

- **现状**：上传后只显示「已完成 / 失败」；扫描 PDF 解析为空只报一句错；切分、主题、标签全部固定或人工。
- **痛点**：用户以为资料已入库，提问却召回不到；重复资料、错放主题、超短文档无人提示；「垃圾进 → 垃圾出」没有任何可见度。
- **Agent 方案**：
  - 能力：检查每份资料的字符数/页数/空页比例、疑似重复、主题与标签建议、覆盖缺口（哪些主题只有 1 份资料）、可问答性抽测（自动生成 3 个探针问题看能否召回）。
  - 交互：入库完成弹「体检报告」（分数 + 3 类问题 + 一键修复）；知识库页常驻「体检」入口。
  - 触发：上传完成后、用户手动发起、Embedding 模型切换后。
- **价值**：把「不知道为什么问不到」变成可解释的报告；目标是扫描件检出率 100%（先检出，OCR 作为可选后续）、无命中提问占比从当前基线降到 10% 以下、主题/标签整理时间从每份 3～5 分钟降到 30 秒内（待埋点校准）。

### Tier B：增强项（可作为亮点内部的支撑能力）

#### B1. 多跳问答 Agent

- **现状**：一次检索、一次生成；多源上限 3；没有子问题拆解，也没有「先澄清再回答」。
- **痛点**：「比较 A 和 B 在三种场景下的差异」这类问题容易只答一半；引用编号合法但未必支持结论。
- **Agent 方案**：问题拆解 → 每个子问题独立检索 → 合并去重 → 逐条核对「引用是否支持这句话」→ 信息不足时反问一个最关键的问题。
- **交互/触发**：问答页自动判断；复杂问题显示「拆成了 3 个子问题」可展开。
- **价值**：复杂问题一次答全率目标 +25%；把「答错但看起来很像」的比例降下来。**不作为独立亮点**，作为教练与诊断的底层能力。

#### B2. 出题蓝图 Agent

- **现状**：按题型数量一次性生成，难度固定 medium，校验格式与答案字母范围，不校验覆盖。
- **痛点**：同一主题反复出相似题；简单题/难题比例不可控；生成结果可能集中在某一章。
- **Agent 方案**：先读主题覆盖与历史错题，生成「出题蓝图」（章节 × 难度 × 题型），再逐块生成并去重。
- **价值**：出题覆盖度可量化；重复题比例目标降到 5% 以下。

#### B3. 笔记事实核对 Agent

- **现状**：模板化一次起草，AI 补写有标记；人工定稿后不参与检索。
- **痛点**：AI 写的段落可能过时或与资料冲突；用户要逐段对照原文。
- **Agent 方案**：起草后增加「核对」步骤：逐段找来源、标出无依据段落、给出可选改写；不自动改定稿。
- **价值**：定稿前的人工核对时间目标减半；不改变「人工定稿」的产品原则。

#### B4. 回顾报告教练化

- **现状**：一次生成五段式报告，数字来自聚合，但建议偏通用。
- **痛点**：报告读完不知道下一步具体做什么；与计划不联动。
- **Agent 方案**：生成前先查错题与计划执行，报告最后直接产出「下周 3 个动作」并写入计划草稿。
- **价值**：报告到行动的转化率可测；与 A1 共用工具，改造成本低。

#### B5. 协作投稿预审 Agent

- **现状**：member 投稿进入 `pending_review`，owner 人工预览后批准/驳回。
- **痛点**：owner 成为瓶颈；重复资料、低质量资料要人工发现。
- **Agent 方案**：预审摘要（主题、页数、重复度、敏感内容提示、建议决定），owner 一键确认。
- **价值**：审核时间目标降低 50%；不替代 owner 决定。

#### B6. 学习路径/知识地图

- **现状**：只有主题与标签，没有概念之间的关系。
- **痛点**：用户不知道「学完这章接下来学什么」，主题之间是孤岛。
- **Agent 方案**：从片段中抽取概念与先修关系，生成可点击的知识地图与缺口。
- **价值/风险**：差异化强，但抽取质量与维护成本高；建议等体检 Agent 把资料质量稳定后再做。

### Tier C：不建议 Agent 化（保持确定性）

| 环节 | 原因 |
|---|---|
| 客观题判分 | 规则判分可复现、可解释；交给模型只会引入随机性 |
| 权限/空间隔离 | 必须 fail-closed，不能让模型决定 |
| 检索召回主流程 | 向量 + FTS + 阈值是可控的；Agent 只应做「拆问题/核对」，不应替代召回 |
| 简答题自动判分 | 当前自评是诚实的设计；模型判主观题不可靠 |
| 全自动答题/代写 | 与学习产品定位冲突，且有学术诚信风险 |

## 3. 评分与筛选

权重：用户价值 30%、差异化 25%、用户感知 20%、数据就绪 15%、实现风险 10%（风险越低分越高）。

| 场景 | 价值 | 差异 | 感知 | 数据 | 风险 | 加权 | 结论 |
|---|---:|---:|---:|---:|---:|---:|---|
| 错题诊断与补救 | 5 | 5 | 5 | 5 | 2 | **4.90** | 核心 2 |
| 学习教练 | 5 | 5 | 5 | 4 | 2 | **4.75** | 核心 1 |
| 知识库体检 | 5 | 5 | 4 | 5 | 3 | **4.60** | 核心 3 |
| 多跳问答 | 5 | 4 | 5 | 5 | 3 | 4.55 | 支撑能力 |
| 回顾教练化 | 4 | 4 | 4 | 5 | 2 | 4.15 | 随教练一起做 |
| 出题蓝图 | 4 | 3 | 4 | 5 | 2 | 3.95 | 二期 |
| 笔记核对 | 4 | 3 | 4 | 5 | 2 | 3.95 | 二期 |
| 知识地图 | 4 | 5 | 4 | 3 | 4 | 3.90 | 观望 |
| 联邦选源 | 3 | 4 | 3 | 3 | 3 | 3.25 | 维持现状 |
| 投稿预审 | 3 | 3 | 2 | 4 | 2 | 2.95 | 有余力再做 |

**筛选逻辑**：先修「数据可信」（体检），再做「错题归因」，最后做「长期教练」。三者共用同一套证据链与工具层，能形成叠加效应。

## 4. 三个亮点方向的落地路径

### 4.1 学习教练 Agent

**一句话价值**：不是给你一份计划，而是每周陪你改计划。

**用户感知点**
- 侧栏 Agent 分组下的「学习计划」升级为「教练」；计划卡片可直接勾选完成。
- 每周一生成「教练复盘」：本周完成率、变化原因、下周改动（带 diff）。
- 每个调整都能点开「为什么改」，看到引用的错题/练习/资料。

**Agent 设计**
- 角色：只做「观察 → 判断 → 调整计划」，不判分、不改资料、不自动答题。
- 新工具：`get_plan`、`record_checkin`、`update_plan_item`、`replan`（继续复用现有 5 个只读工具）。
- 约束：单次最多 6 步；只写 `study_plans` 与 `plan_items`；任何数字必须来自工具；重排必须保留用户锁定的任务。

**分阶段**
- P0 数据与埋点：计划拆成可勾选条目（`plan_items`），记录完成/跳过/顺延；补事件 `plan_checkin`、`replan_started/accepted`。
- P1 MVP：日勾选 + 周复盘 + 一键重排；重排展示 diff 与证据；失败可回滚到旧计划。
- P2 主动：连续两天未完成时，询问「压缩 / 换顺序 / 休息一天」；不自动修改，需用户确认。
- P3 长期：跨主题目标（如「四周通过期末」），教练按月拆周。

**技术可行性验证**
- 10 组模拟数据（空库/单主题/多主题/全勤/连续缺席）跑通重排；6 步上限不破。
- 每个计划数字可回溯到某一步工具返回；无法回溯则拒绝生成。
- 旧计划可回滚；并发勾选不丢数据；SSE 中断后重连不重复写。

**量化目标（目标值，待校准）**
- 计划创建时间：30～60 分钟 → 5 分钟以内。
- 7 天计划执行率：基线埋点后 +15pp。
- 次周回访率：+10%。
- 重排接受率：≥50%（低于则说明教练判断不可信）。

**差异化**
| 通用 AI 学习产品 | A4S 教练 |
|---|---|
| 生成一份计划，结束 | 计划 → 勾选 → 观察 → 重排 |
| 建议不可追溯 | 每个调整能点回错题/练习/资料 |
| 数据在云端，黑盒 | 全量本地，可导出、可撤销 |

### 4.2 错题诊断与补救 Agent

**一句话价值**：错题不止收进来，还要告诉你为什么错、3 分钟补上。

**用户感知点**
- 错题卡片新增「诊断」；结果分三段：为什么错 / 3 分钟补漏 / 3 题验证。
- 验证通过后打「已修复」，并自动进入下一次计划。
- 诊断结论必须带「依据」：错题原文 + 资料片段。

**Agent 设计**
- 角色：归因 + 讲解 + 出验证题；不直接改知识点掌握度，需用户验证通过后才更新。
- 工具：`get_wrong_answer`、`retrieve_chunks`、`generate_micro_lesson`、`generate_verification`、`mark_mastered`。
- 约束：诊断只引用真实片段；验证题必须同知识点且不与原题重复；单次最多 4 步。

**分阶段**
- P0 错误分类法：概念混淆 / 步骤缺失 / 计算粗心 / 审题偏差；先用规则 + 模型混合打标，人工抽检 30 条建立评估集。
- P1 单题诊断 MVP：错题详情页「诊断」；输出三段式；验证题 3 道；记录 `diagnosis` 与 `verification`。
- P2 批量与计划联动：按知识点聚合「本周最该补的 3 个漏洞」；一键加入教练计划。
- P3 掌握度曲线：同知识点多次验证结果形成掌握度，驱动出题难度。

**技术可行性验证**
- 30 道人工标注错题上，归因准确率 ≥80%；每条诊断至少 1 条真实引用。
- 验证题与原题相似度低于阈值；3 题全部针对同一知识点。
- 验证未通过不写「已修复」；用户可手动推翻诊断。
- 无资料可引用时，明确说「资料不足，只能给通用讲解」，不伪造来源。

**量化目标（目标值，待校准）**
- 单题补救时间：10～15 分钟 → 3 分钟以内。
- 同知识点 7 天内二次错误率：-20%。
- 诊断后 48 小时内完成验证的比例：≥60%。
- 用户对诊断「有帮助」的比例：≥70%。

**差异化**
| 普通错题本 | A4S 诊断 |
|---|---|
| 收集、筛选、重练 | 归因 + 讲解 + 验证 + 回写 |
| 重练原题 | 换 3 道同知识点题验证迁移 |
| 不知道为什么错 | 每条结论带资料依据 |

### 4.3 知识库体检 Agent

**一句话价值**：资料导进来先体检：哪几页没解析、和哪份重复、该放哪个主题。

**用户感知点**
- 上传完成弹「体检报告」：健康分、问题清单、一键修复。
- 知识库页常驻「体检」入口，显示上次体检时间与未处理问题数。
- 问题可定位到具体文档/页码；修复前后可对比。

**Agent 设计**
- 角色：检查 + 建议 + 执行安全的修复；删除/覆盖必须二次确认。
- 工具：`inspect_document`、`detect_duplicates`、`suggest_topic_tags`、`probe_answerability`、`apply_fix`。
- 约束：只做可逆操作（重切分、改主题、合并重复）；不自动删除；每份资料最多 3 个修复动作。

**分阶段**
- P0 体检指标：字符数/页数、空页比例、0 片段文档、疑似重复（标题 + 首段哈希）、主题覆盖。
- P1 报告与修复：入库后生成报告；支持「重新切分」「改主题/标签」「合并重复」；记录修复日志。
- P2 可问答性抽测：每份资料生成 3 个探针问题，跑检索看能否召回；失败标「可能无法问答」。
- P3 OCR 兜底：检测扫描页，提示安装 OCR 依赖或改用可复制文本；不默认开启重依赖。

**技术可行性验证**
- 20 份样本（正常/扫描/超短/重复/错主题）上，空页与 0 片段识别率 100%，重复识别准确率 ≥90%。
- 修复幂等；重切分后 chunk 数变化可解释；失败可回滚。
- 体检不阻塞上传主流程；大文件后台执行。

**量化目标（目标值，待校准）**
- 「不知道为什么问不到」的支持请求下降 50%。
- 无命中提问占比：当前基线 → 10% 以下。
- 主题/标签整理时间：3～5 分钟/份 → 30 秒内。
- 体检报告处理率（用户点开并处理至少一项）：≥40%。

**差异化**
| 普通 RAG 工具 | A4S 体检 |
|---|---|
| 导入即结束 | 导入后给质量报告 |
| 扫描件静默失败 | 明确标出未解析页 |
| 重复/错放无人管 | 重复检测 + 主题建议 + 一键修复 |
| 不知道能不能问 | 探针问题验证可问答性 |

### 4.4 多智能体结构：教练 + 体检如何协作

**结论：可以，但要「有限多智能体」，不是自治蜂群。**
推荐结构 = 1 个协调者 + 2 个专业角色 + 1 个审核者 + 1 个唯一写入口，最多 4～5 个角色；
角色之间不自由对话，只通过**类型化发现（Finding）**和**共享证据库**交接。

```
用户目标 / 上传
      │
      ▼
┌───────────────┐   预算 / 权限 / 证据库
│ Coordinator   │◀──────────────┐
│ 选道 + 合流    │               │
└──┬────────┬───┘               │
   │        │                   │
   ▼        ▼                   │
┌────────┐ ┌──────────────┐     │
│ Coach  │ │ KB Inspector │     │
│ 观察+规划│ │ 体检+修复建议 │     │
└──┬─────┘ └──────┬───────┘     │
   │ findings/plan │ findings/fix│
   └──────┬────────┘             │
          ▼                      │
   ┌────────────┐                │
   │ Verifier   │ 数字/引用/权限  │
   │ 通过/打回   │────────────────┘
   └─────┬──────┘
         ▼
   ┌────────────┐
   │ Writer     │ 唯一写操作
   │ 计划/修复   │
   └────────────┘
```

#### 角色与权限

| 角色 | 职责 | 关键工具 | 写权限 |
|---|---|---|---|
| Coordinator | 判断走教练道还是体检道；分配预算；合并结果；对用户输出 | 路由、预算、Finding 读取 | 无 |
| Coach · Observer | 读进度、错题、体检发现，形成「本周判断」 | `get_progress` `list_weak_points` `list_wrong_answers` `read_findings` | 无 |
| Coach · Planner | 基于判断提出计划条目与重排理由 | `get_plan` `propose_plan` | 无（只出提案） |
| KB Inspector | 检查空页、0 片段、重复、主题覆盖、探针问答 | `inspect_document` `detect_duplicates` `probe_answerability` | 无 |
| KB Fixer | 提出可逆修复：重切分、改主题、合并重复 | `propose_fix` | 无（只出提案） |
| Verifier | 校验数字是否来自工具、引用是否真实、权限是否允许；可打回一次 | `verify_claims` | 无 |
| Writer | 唯一落库者：写计划、写修复动作、写运行记录 | `commit_plan` `apply_fix` | **唯一** |

#### 两条泳道，不互相调用

- **体检道（后台）**：上传完成 → Inspector 逐份检查 → Fixer 生成修复提案 → Verifier 校验 → 写 `agent_findings` 与 `fix_actions`；不阻塞上传主流程。
- **教练道（前台/每周）**：用户点「教练复盘」或周定时 → Coordinator 启动 → Observer 读取进度与体检发现 → Planner 出计划提案 → Verifier 校验 → Writer 写计划。
- **交接方式**：体检道只把「事实」写进 `agent_findings`（如「文档 A 第 3 页无文本」）；教练道通过只读工具读取，**不直接调用体检角色**。这样两条链路可独立测试、独立失败、独立重跑。

#### 为什么这样拆，而不是让 Agent 互相对话

| 自由对话式多 Agent | 本方案（黑板 + 角色契约） |
|---|---|
| 上下文爆炸、谁说了什么难以复盘 | 每个角色只读自己的输入与 Finding，上下文小 |
| 出错后无法定位是哪一轮对话导致 | 每次运行有 `agent_runs / agent_steps / verdict`，可回放 |
| 多角色同时写库会冲突 | 只有 Writer 能写，天然避免并发写 |
| 角色越多越像演示 | 4～5 个角色，每个都有明确工具与验收 |

#### 消息与数据契约（先定契约，再写 Agent）

```json
{
  "id": "kb:doc_123:empty_pages",
  "kind": "kb_issue",
  "claim": "第 3、7 页没有可抽取文本",
  "evidence": [{ "document_id": "doc_123", "page": 3 }, { "document_id": "doc_123", "page": 7 }],
  "confidence": 0.95,
  "producer": "inspector",
  "created_at": "2026-11-26T10:00:00+08:00"
}
```

- `Finding`：只有事实与证据，不含建议；所有角色可读。
- `Proposal`：计划条目或修复动作，必须引用至少 1 条 Finding。
- `Verdict`：`pass / reject`，附拒绝原因；被拒的 Proposal 不得进入 Writer。
- `agent_runs / agent_steps`：记录角色、入参摘要、工具返回、耗时、token；用于回放与评估。

#### 预算与安全边界

- 单次运行总步数 ≤ 12；角色交接 ≤ 3 次；Verifier 打回后最多重试 1 次。
- 每个角色声明自己的工具白名单；Coordinator 无权调用写工具。
- 体检修复只允许可逆动作；删除/覆盖必须用户二次确认。
- 体检失败不影响上传；教练失败回滚到上一份计划。
- 任何 Finding 没有证据，直接丢弃，不进入下游。

#### 用户感知：把「协作」翻译成人话

不要展示「Agent A 对 Agent B 说」。时间线按角色分组，但用用户语言：

```
体检员  发现 3 个问题：2 页未解析、1 份重复
观察员  本周完成 2/7，错题集中在「分组密码」
规划员  建议周三改为补漏，把原计划的两道题顺延
审核员  4 个数字都能对上出处，通过
```

用户只看到「谁发现了什么、因此改了什么」，并可展开每一步的原始数据。这就是多智能体相对单 Agent 的**可解释性红利**。

#### 技术可行性验证标准

1. 每个角色有独立契约测试，可用固定输入跑通，不依赖其他角色。
2. Verifier 在 30 条「数字无出处 / 引用不存在 / 越权写」样本上拦截率 100%。
3. 预算测试：人为制造循环，运行在 12 步内终止并给出原因。
4. 体检道单份文档失败不影响其他文档，也不阻塞上传。
5. 教练道只读 Finding，不直接读体检道的内部状态；跨道测试可独立替换。
6. 端到端 10 个场景（空库、单主题、连续缺席、重复文档、扫描件、共享库）全部可回放、可回滚。

#### 成本与风险

| 风险 | 表现 | 对策 |
|---|---|---|
| 时延变长 | 多角色串行 | Observer 与 Inspector 并行；体检放后台；SSE 流式 |
| token 成本上升 | 每个角色一次调用 | 角色提示词只带必要 Finding；缓存；只在数据变化时重跑 |
| 调试困难 | 不知道哪一步坏了 | `agent_runs` 全量记录；每个角色可单独回放 |
| 写冲突 | 多角色同时改计划 | 唯一 Writer；版本号 + 乐观锁 |
| 用户困惑 | 看到一堆角色名 | 只展示「体检员/观察员/规划员/审核员」四个人话角色，隐藏内部提示词 |
| 过度设计 | 为多 Agent 而多 Agent | MVP 只上 4 个角色；角色数 >6 或出现复杂循环时再评估图编排框架 |

#### 为什么暂不引入 LangGraph

当前只有两条泳道、4～5 个角色、无跨轮循环，现有 `plan_agent` 的循环 + 一个轻量 Coordinator 足够；
引入图编排框架会增加依赖、学习成本与调试面。等出现「多角色多轮协商」或角色数超过 6 个时再评估，ADR-03 的结论暂不改变。

#### 分阶段落地（对应第 7 节）

- P1（已完成）：只拆教练道（Coordinator + Observer + Planner + Verifier + Writer），验证多角色是否真的比单 Agent 更稳。
- P2：加体检道（Inspector + Fixer），后台产出 Finding。
- P3：教练道读取体检 Finding，形成「体检 → 计划」的跨道协作；周定时主动跑一次。
- P4：把错题诊断作为第三个 specialist 插入，不改变主结构。

> **落地进度（2026-11-27）**：P1 已落地。角色代码在 `backend/client/services/agents/`，运行与步骤写入 `agent_runs` / `agent_steps`，`GET /api/plan/runs/{run_id}` 可回放；审核为确定性规则（长度 + 三段结构 + 依据数字核对），打回最多重试 1 次，只有 Writer 能调 `save_plan`。对外仍是 6 步，前端时间线新增角色徽标。冒烟脚本 61 项断言全部通过。P2 体检道同日落地：`Inspector` 逐份巡检、`Fixer` 只出建议、`Verifier` 丢弃无依据提案，`POST /api/kb-health/run` 手动触发，不调模型也不写业务表；探针召回留到 P2.1，冒烟 31 项断言通过。

> 判断多智能体是否成功的标准不是「角色多」，而是：**Verifier 拦截了多少错误、跨道协作减少了多少重复劳动、用户是否更容易理解为什么改。**

## 5. 统一的产品与交互原则

1. **一个入口，三种能力**：侧栏 Agent 分组下先放「教练」，诊断与体检从具体页面进入，不堆第四、第五个导航项。
2. **过程可见**：沿用学习计划的 SSE 步骤条；每个 Agent 都有「它在看什么 / 它决定了什么」。
3. **证据可点**：任何结论、数字、建议都能点回原文片段或原始记录。
4. **写操作可撤销**：教练改计划、体检改主题、诊断回写掌握度，都要有「撤销 / 恢复」。
5. **不确定就承认**：资料不足、检索不到、模型不确定时，明确说「不知道」，不用通用知识伪装成资料结论。
6. **不做通知轰炸**：主动提醒每周最多 1 次，且必须带一个可执行动作。

## 6. 度量与实验设计

**北极星指标**：周闭环完成率 = 完成「计划 → 练习 → 诊断/补漏 → 复查」的用户 / 当周活跃用户。

**每个亮点的主指标**
- 教练：计划执行率、重排接受率、次周回访率。
- 诊断：补救完成率、同知识点二次错误率、诊断有帮助率。
- 体检：报告处理率、无命中提问占比、0 片段文档占比。

**护栏指标**
- Agent 单次 p95 时延（教练 < 90s，诊断 < 30s，体检后台不阻塞）。
- 单次 token 成本上限。
- 错误建议率（用户点「没用/不对」的比例）。
- 撤销率（过高说明判断不可信）。
- 任何写操作的数据一致性（重复提交、断线重连）。

**实验方式**
- 本地产品不适合传统 A/B：用「功能开关 + 前后对比 + 用户主动开启」。
- 每个亮点上线前先建 30～50 条评估样本（计划/错题/文档），跑离线评估，再放量。

## 7. 分阶段路线图

| 阶段 | 内容 | 依赖 | 验收 |
|---|---|---|---|
| P0 前置 | 契约（Finding / Proposal / Verdict）、`agent_runs/steps`、评估集、预算与撤销机制 | 无 | 契约测试通过；每次运行可回放 |
| P1 v0.3 | 教练多智能体 MVP：Coordinator + Observer + Planner + Verifier + Writer；计划条目 + 勾选 + 周复盘 + 重排 | P0 | 10 组场景；12 步内完成；数字 100% 可溯源；Verifier 拦截率 100% |
| P2 v0.4 | 体检道：Inspector + Fixer（后台）+ `agent_findings` + 体检报告 + 一键修复 | P0 | 20 份样本识别率达标；扫描件检出 100%；修复幂等可回滚 |
| P3 v0.5 | 跨道协作：教练读取体检 Finding；周定时主动复盘 | P1/P2 | 10 个跨道场景；体检失败不阻塞教练；周闭环完成率提升 |
| P4 可选 | 诊断 specialist + 跨主题目标 + 知识地图 | P1/P3 | 30 条标注准确率 ≥80%；不改变主结构 |

> 顺序理由：教练复用现有 L3 能力，最快形成感知；体检为教练提供「资料是否可信」的事实底座；先单道验证多角色是否真的更稳，再做跨道协作。诊断作为可插拔 specialist 放到最后，不阻塞前两条链路。
