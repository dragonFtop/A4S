# 哪里该用 Agent，哪里不该用

> 这份文档回答两个问题：**这个项目里现在有没有 Agent？** 以及**如果要加，加在哪、为什么其它地方不加。**
>
> 初版写于 v0.1 交付后；v0.2 落地学习计划后追加了实现说明。文中所有数字都是从代码里数出来或实测出来的，不是估计。

---

## 0. 结论

全项目 16 个决策点里，**只有「学习计划」一个点该用 Agent**，其余 15 个用固定规则或一次性调用更合适。

v0.1 时项目里**没有任何 Agent**；v0.2 按本文的判据只加了**一处**：学习教练（入口 `client/services/plan_agent.py`，
实现 `client/services/agents/`），写 `study_plans` 一张表，过程通过 SSE 逐步推给前端。
v0.2.1 起它内部拆成四个有限角色（观察 / 规划 / 审核 / 写入），但对外仍是一个能力点。

v0.2.1 另加了**知识库体检道**（FR-16）：巡检 / 修复建议 / 审核三个固定角色，检查项与建议都由代码决定，不调模型。
按本文判据它**不算 Agent**，但复用同一套黑板与运行账本，所以单独说明，避免被当成第二个自主能力。
除此之外仍是 **RAG 流水线 + 固定编排**——每一步做什么、什么时候做，都是代码写死的。

## 1. 判据：四个问题

判断一段代码是不是 Agent，不看它叫什么名字，看这四件事：

| # | 问题 | 是 → | 否 → |
|---|---|---|---|
| 1 | **下一步做什么，谁决定？** | 模型决定 → 有自主性 | 代码写死 → 是流水线 |
| 2 | **有没有「动作 → 观察 → 再决定」的回路？** | 有工具调用循环 | 一次性输入输出 |
| 3 | **失败了能不能自己换一条路？** | 模型重新规划 | 只能按预定义的降级走 |
| 4 | **同一输入跑两次，结果是否必须一致？** | —— | —— |

第 1、2 问是**必要条件**，两个都「是」才算 Agent。第 3 问是加分项。
第 4 问是**反向红线**：凡是结果必须可复现的地方（判分、索引、统计），放 Agent 是负债不是资产。

按这个标准核对现在的代码：除学习计划外，单次调用大模型的地方只有 5 处——

```
chat_service.py    一次生成（检索到了资料）
chat_service.py    一次生成（没检索到，用通用知识）
note_service.py    一次生成（起草笔记）
llm_generator.py   一次生成 + 一次重试（出题，格式不合格重来）
review_service.py  一次生成（报告的三段分析）
```

学习计划是唯一例外：观察员在 3 步预算内让模型选择下一个只读工具，规划员基于事实写计划，审核员核对后才由记录员写入。
出题那处的重试仍然不算 Agent——判断标准是代码写的（选项数、答案字母范围）不合格就重来，
不是模型自己的决策。

所以：**当前项目是一个「RAG 流水线 + 一个受限 Agent」的混合体，而不是 Agent 系统。**

## 2. 逐点判定

| # | 决策点 | 现在怎么做 | 判定 | 为什么 | 硬塞 Agent 会怎样 |
|---|---|---|---|---|---|
| 1 | 资料解析（PDF/Word/MD/TXT） | 按扩展名选解析器 | **不用** | 格式由扩展名决定，没有判断空间 | 同一份 PDF 两次解析出不同结构，没法排查 |
| 2 | 文本切分 | 按标题层级 + 长度规则 | **不用** | 切坏了调参数重切即可，不需要现场决策 | 每次切分边界不同，索引不可复现 |
| 3 | 向量化与入库 | 固定模型 + sqlite-vec | **不用** | 纯计算，没有决策 | 纯浪费 |
| 4 | 检索（Top-K + 相似度阈值） | 向量检索 + 阈值 0.42 | **不用** | 这是**度量问题**，不是决策问题。相似度是个数字，阈值能测出来（见下文）。模型说「相关」不给分，调不准也解释不清 | 用户问「为什么这条被选中」，答不上来 |
| 5 | 相似度擦边时的取舍（0.42~0.55） | 提示词追加一段判断指令 | **半自主，但不是 Agent** | 模型确实在做判断，但判断范围被锁死在一句话里：能答/答一半/答不了。没有工具、没有循环、结果不影响下一步动作 | 扩大成「自己决定再检索什么」就变成两次 LLM 调用，延迟翻倍，收益不明 |
| 6 | 问答生成 | 检索 → 一次生成 | **不用** | 检索已经把材料给全了，再让它决定「还要查什么」等于重复检索 | 延迟 ×2~3，成本 ×2~3，准确率不涨 |
| 7 | 无资料兜底作答 | 声明 + 一次生成 | **不用** | 一次调用就够，没有中间状态 | 为了「像 Agent」硬加一步反思，只增加失败点 |
| 8 | 笔记起草 | 一次生成 + 人工定稿 | **不用** | **人已经在回路里**，自主性无处发挥 | 模型和人抢着改，反而增加核对成本 |
| 9 | 出题 | 生成 + 结构化校验 + 重试 | **不用**（但用了机械循环） | 判断标准是代码写的（题型/选项数/答案格式），不是模型判断的。这个循环叫**校验重试**，不叫 Agent | 让模型自评「这题出得好不好」，两次评分不一致，题目质量就不可比 |
| 10 | 判分 | 规则判分（客观题逐项比对） | **不用** | 答案必须确定：同一份答卷今天 80 分、明天 85 分，错题本就失去意义 | 直接破坏 FR-05 |
| 11 | 错题归档 | 同题累加次数 | **不用** | 纯规则：按题干哈希去重 | 同一道题被建出三条记录 |
| 12 | 回顾报告 | 程序算数字 + 模型写三段文字 | **不用** | 分工已经是最优：数字一旦交给模型就会编（这个项目在 M5 就是为此把数字锁在程序里） | 报告里的正确率开始出现「约」「大概」 |
| 13 | 定时发送 | APScheduler，固定时间 | **不用** | 时间是确定的 | 无意义 |
| 14 | 今日建议（概览页） | 规则拼装三条 | **可以升级，但方向不是 Agent** | 现在按「空库 → 有资料没练 → 有错题 → 正常」的优先级取第一条。升级应该是**打分排序**（更可解释），而不是让模型现场想 | 每次刷新建议都不一样，用户会觉得这功能在瞎猜 |
| 15 | **学习计划** | **v0.2.1 已实现**：有限多智能体（观察 / 规划 / 审核 / 写入），对外 6 步，5 个工具，SSE 逐步推送 | **该用 Agent** ⭐ | 见第 3 节 | —— |
| 16 | 复习时间安排（间隔重复） | 还没有 | **用算法，不用 Agent** | 「下次什么时候复习」有成熟公式（SM-2 / FSRS），可解释、可复现、可调参。让模型排期，用户问「为什么是后天」就答不上来 | 排期不可复现，也无法调参优化 |

**一句话记法**：只要判断标准能写成代码（格式、数值、优先级、时间），就别用 Agent；只有当「下一步做什么」本身依赖对内容的理解时才用。

## 3. 唯一该用 Agent 的点：学习计划

### 3.1 它为什么符合判据

| 判据 | 这个点的情况 |
|---|---|
| 下一步由谁决定 | **必须由模型**。「先补密码学还是先补数据结构」取决于错题文本里到底是什么知识点，规则只能按错误次数排，排不出「这两个错误其实是同一个概念没懂」 |
| 有没有回路 | **天然有**：查统计数据 → 发现薄弱点 → 决定要不要现在出一套题 → 出完了 → 根据结果写计划。顺序不固定，有时不需要出题 |
| 失败能否换路 | 能：出题失败（片段不够）就退回「只给复习建议，不出题」 |
| 结果要不要一致 | **不要**。计划每次都不同是特性，不是 bug——它反映的是当下的数据 |

### 3.2 它需要什么工具

```python
get_progress()                  # 概览统计：资料数、练习数、平均分、错题数
list_weak_points(limit=5)       # 按错误率排的知识点，带错题原文摘要
list_wrong_answers(limit=20)    # 待复习错题（题干 + 你的答案 + 正确答案）
generate_practice(counts, ...)  # 复用现有出题器，直接出一套针对薄弱点的题
save_plan(markdown)             # 落库（新建 study_plans 表）
```

五个都只是**把已有能力包一层**，不新增业务逻辑——这是控制复杂度的关键。

### 3.3 循环本身只有几十行

```python
for step in range(MAX_STEPS):                 # 硬上限，防止无限循环
    reply = llm.chat(messages_with_tools)
    action = parse_action(reply)              # {"tool": "...", "args": {...}}
    if action is None:                        # 模型给的是最终答案
        break
    result = TOOLS[action["tool"]](**action["args"])
    yield sse("step", {"tool": ..., "ok": True})   # 每一步都推给前端
    messages.append({"role": "user", "content": json.dumps(result)})
```

关键设计只有三条：

1. **步数上限**（比如 6 步）——没有上限的 Agent 就是没有刹车的车。
2. **每个工具返回值截断**（比如 2000 字符）——否则错题原文能把上下文撑爆。
3. **每一步都推 SSE 事件**——前端能看到「查了薄弱点 → 发现 3 处 → 出了 5 道题 → 写了计划」。这是它和普通功能唯一肉眼可见的区别，也是它值得做的理由。

### 3.4 它和工作流的差别在哪

同一句「这周怎么复习」：

- **工作流做法**：固定顺序查统计 → 查错题 → 拼 prompt → 生成一段文字。不管数据是什么，都走完这套。
- **Agent 做法**：先看统计，发现「一题都没做过」→ 直接决定「不用查错题了，建议先做一套入门题」→ 调 `generate_practice` → 拿到题目 → 写计划。**中间跳过了两步，且跳过的理由来自数据。**

这个差别用户能感觉到：工作流会给一个「没做过题的人」推荐「复习错题」。

### 3.5 为什么它不会变成第二个「看不懂的模块」

- 循环 150 行、工具 150 行、接口与建表 100 行左右，总共 400 行上下；
- 工具是 5 个纯函数，每个不超过 20 行，单独能测；
- 循环是 `for + if`，没有并发、没有嵌套状态；
- 失败只有三种出口：步数用尽、模型不按格式、工具报错——都落日志。

对照现在的代码体量（服务层 3261 行），加 400 行是可接受的。但**前提是不要再往里加第二个 Agent**。

### 3.6 它的职责与边界

一句话：**它只对「接下来做什么」负责，不对「做得怎么样」负责。** 诊断与排程归它；执行、评分、内容生产都不归它。

#### 3.6.1 三件正向职责

| 职责 | 具体做什么 | 为什么只能它做 | 用到的工具 |
|---|---|---|---|
| **诊断排序** | 从错题原文里认出「这几道错其实是同一个概念没懂」 | 规则只能按错误次数排 A > B，排不出 B 与 C 同源 | `list_weak_points` / `list_wrong_answers` |
| **决定路线** | 这一轮该补概念还是刷题；样本太少先攒数据；一题没做就先出入门题 | 要看内容再判断，且走几步不固定 | `get_progress` + `generate_practice` |
| **成文收口** | 把决定写成 7 天可执行清单：哪天补什么、练几道、什么算完成 | 前两步的结论要落到人能照着做的粒度 | `propose_plan`（提交审核；真正写入由记录员完成） |

三件里第一件是它存在的理由，第二件是它区别于工作流的地方（见 3.4），第三件只是收尾。

#### 3.6.2 四组边界

**① 能力边界——不生产内容，只调已有能力。**

出题调 `generate_practice`，不自己写题。现成的出题器带结构校验（题型、选项数、答案字母范围）与重试，模型自出的题没有这层保护；两条生成路径并存，题目质量就不可比。

**② 写入边界——只有一个写操作。**

`save_plan` 写 `study_plans` 表，且**只有记录员（Writer）能调**：观察员与规划员的工具白名单里没有写库能力，规划员用 `propose_plan` 提交提案。不改笔记（笔记要人定稿，见第 2 节 #8）、不改错题本（归档按题干哈希，见 #11）、不改题库。**读的一侧敞开，写的一侧只留这一个口子。**

**③ 数值边界——不自己算数。**

计划里出现「平均分 78」「3 个薄弱点」，必须原样来自 `get_progress` / `list_weak_points` 的返回值，不许推演、不许估。这是 M5 的教训复用：数字锁在程序里，模型只写文字。**数字一旦交给模型，就开始出现「约」和「大概」。**

**④ 时间与状态边界——一次会话、一份计划、7 天粒度。**

- 不跨会话记忆，每次从库里重新读；
- 计划是当下数据的**快照**，不是常驻状态；
- 不在后台跑，不循环刷题攒数据（关掉页面就停）；
- 不做月/季度规划：现有数据支撑不住，只能产出漂亮的空话。

#### 3.6.3 失败出口

循环内的出口与 3.5 一致（步数、格式、工具报错），另加两道检查：

| 情况 | 怎么退 |
|---|---|
| 资料 0、练习 0 | **不出计划**，只返回一句引导（「先导入一份资料」）。否则它会开始编「你最近在学什么」 |
| 规划员在预算内没写出 Plan | 返回已收集到的诊断结论，不留半张计划（`no_plan`） |
| 审核连续两次不过 | 同样不写入（`no_plan`），并把 Verdict 理由落进 `agent_steps` |
| 工具报错 | 该步标记失败，允许换路；观察员预算用尽就带着现有事实交棒 |
| 模型不按格式 | 一次纠正，再不行按「预算用尽」处理 |
| 写库失败 | 运行标记 failed，返回 error，不重试（本地 SQLite 写失败通常不是瞬时问题） |

共性：**宁可少给，不编。** 与问答那边「没检索到就声明」是同一条原则。

#### 3.6.4 验收标准

> 计划里每写一个数字、每提一次「你错在哪」，都必须能对回到某一步工具调用；界面上点得开，看得到那一步的入参和返回值。

做不到这条，说明它在猜，边界就是失效的。

这条也回答了 3.5 的担心：输出永远可溯源，最坏的失败模式是「计划写得平庸」，而不是「数字对不上还查不出从哪来」。

> **落地状态（2026-11-27）**：P0 已落地。入口仍是 `client/services/plan_agent.py`（薄转发），
> 角色实现见 `client/services/agents/`（`coordinator` / `observer` / `planner` / `verifier` / `writer`），
> 契约在 `shared/domain/models/agents.py`，运行账本为 `agent_runs` / `agent_steps`。
> 预算：工具步 ≤6、模型调用 ≤12、交接 ≤3、审核重试 ≤1；审核是确定性规则，不调模型。
> `GET /api/plan/runs/{run_id}` 可回放一次运行；`smoke_m7.py` 的 73 项断言覆盖空库、角色交接、审核拦截、回放与失败出口。
> P3 跨道协作：规划前由协调员读最近一次体检，把高危 / 中危资料问题并入黑板（`read_kb_health` 一步）；读取失败降级为空。

## 4. 为什么不做「问答 Agent」和「温习 Agent」

| 想法 | 现状够不够 | 加 Agent 得到什么 | 加 Agent 失去什么 |
|---|---|---|---|
| 问答 Agent | 检索 → 生成已经是完整闭环，瓶颈在阈值与引用（本轮已修） | 多轮检索、自我纠错——理论上能提高召回 | 延迟和成本翻倍；「为什么这次查了 3 遍」无法解释；本项目真正的问题是阈值漏，已经在 0.42 解决 |
| 温习 Agent | 错题本 + 回顾报告 + 定时任务已覆盖 | 模型自己决定复习节奏 | 排期不可复现、不可调参，出问题没法查；用 SM-2 更合适 |

把这两个叫 Agent，唯一变化是模块名和 README 的措辞。

## 5. 「改名」的代价

如果只改名字不改逻辑：

- 审代码的人打开 `chat_service.py`，看到的是一个函数顺序调用 `retrieve()` 和 `stream()`，没有循环——「Agent」这个词立刻变成减分项；
- 面试或答辩时被问「你的 Agent 怎么决定下一步」，答「代码里写死的」，比不做 Agent 更尴尬；
- 三个「Agent」共享同一个 `_stream_answer`，反而是最容易被看穿的地方。

**判断标准很简单**：能不能在界面上给人看一段「模型自己决定先查 A、再查 B」的过程记录？能，就是 Agent；不能，就老实叫模块。

---

## 6. 以后加功能时的自查清单

想给新功能贴「Agent」标签前，先过这四条：

1. 下一步做什么，是不是真的需要模型判断？——能写成 if-else 的，写 if-else。
2. 有没有至少两次「动作 → 观察」？——只有一次调用的，是功能不是 Agent。
3. 结果需不需要可复现？——判分、索引、统计、排期：**必须可复现，一律不用 Agent**。
4. 过程能不能展示给用户？——不能展示的自主性，用户感知不到，只剩成本和不确定性。

四条里第 1、2 必须为「是」，第 3 必须为「否」，第 4 强烈建议为「是」。

| 碳酸锂的提纯工艺有哪些 | 0.327 | **否** |
| 今天北京的天气怎么样 | 0.188 | 否 |
| 帮我写一首关于秋天的诗 | 0.132 | 否 |

原来的阈值 0.3 会把 pandas（0.459）和碳酸锂（0.327）都放进来——这就是「模型对着无关片段硬答」的根源。
现在 0.42 挡住噪声，0.42~0.55 之间交给提示词让模型自己判断。

这条经验同样适用于判断要不要用 Agent：**能用数字说清的地方，先量一遍，再决定要不要交给模型。**
