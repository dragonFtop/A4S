## 1. 背景与愿景

### 1.1 为什么做

AI 时代可用的工具有很多，但学生的需求被切得很碎：资料在一个地方、笔记在另一个地方、备考计划在脑子里、通知散落在各个群和平台。A4S 的目标是把这些"分散的 AI 能力"收敛成一个 **面向大学生的 ALL in AI 学习助手**，用 Agent + RAG 把资料、练习、回顾串成一条完整的成长闭环。

### 1.2 产品愿景

> 让每一个大学生都能拥有一个属于自己的、懂自己资料的学习伙伴——资料进去，知识与练习出来；越用越懂你。

### 1.3 v0.1 的产品假设

我们假设：**"资料 → 问答 → 练习 → 错题 → 回顾"这条闭环，本身就是学生最刚需、最高频的场景。** 如果这条闭环跑通且体验足够好，后续的备考规划、校园通知、多 Agent 团队才有生长的基础。因此 v0.1 只验证这条闭环。

## 2. 产品形态与部署

| 项   | 决策                                                                |

## 3. 范围与非目标

### 3.1 本期范围（v0.1 P0 + v0.2 增量）

1. **知识库底座**：资料导入与索引（PDF/MD/TXT/DOCX + 粘贴文本）。
2. **标签化知识库**：资料按「主题」归属、按「标签」横向切分；主题与标签作为问答、出题、错题、回顾的**范围参数**贯穿全产品。
3. **RAG 问答**：基于知识库的自然语言问答，带引用溯源，可限定在某主题内提问。
4. **练习检测**：基于知识库出题（选择/判断/简答）、作答判分、错题本。
5. **电子笔记**：手写笔记 + LLM 按模板整理成结构化草稿，人工编辑确认后定稿（AI 起草 / 人工定稿两阶段）。
6. **回顾与触达**：定期生成含错题分析的回顾报告（按主题分组），并邮件推送。
7. **账号与空间（v0.2）**：本地注册登录、个人空间 / 学习小组、成员权限、投稿审核、只读共享（详见 `docs/CLIENT_SERVER_SPLIT.md`）。
8. **学习计划（v0.2 / FR-14）**：按资料与错题排 7 天计划，Agent 循环过程可展开查看。

### 3.2 后续版本（P1，本期不做）

- 简答题 LLM 辅助评分
- 错题掌握度曲线、知识点熟练度模型
- 间隔重复排期（SM-2 / FSRS）
- 切分策略可视化调参
- **笔记回灌知识库**（定稿笔记参与向量检索）
- **错题一键整理成笔记**（`source_type='wrong_answer'`）
- **按主题/标签导出资料包（.zip）**
- 笔记版本历史与差异对比
- 所见即所得编辑器（替换 Markdown 双栏）
- PPT/Excel/图片 OCR
- 多收件人、邮件模板定制
- 回顾报告补发（关机期间错过的周期）
- 本地插件协议（L1，v0.5 可选）

> 已经落地、不再列为后续项：网页 URL 导入（2026-11-25）、混合检索（FTS5 + 向量双路召回）、客户端/服务端拆分与空间协作（v0.2）。

### 3.3 明确非目标（本期绝不做）

| 非目标                  | 原因                                                |
| -------------------- | ------------------------------------------------- |
| 云端多租户、公网账号体系、云同步     | 本地账号与空间已在 v0.2 落地；再往上做公网身份、多租户计费与云同步属于运营问题，与"本地优先"定位冲突 |
| 校园通知抓取（模块③）          | 依赖爬虫与平台授权，合规与维护成本高                        |
| 模拟面试等多 Agent 团队（模块④） | 需要 Agent 编排（LangGraph），待闭环验证后再上                   |
| 联网搜索、多模态（图片/语音）问答    | 扩大成本与不确定性，非核心闭环                                   |
| 原生桌面程序（作为唯一形态）        | Tauri 外壳已预留，但 WebUI 仍是主形态；不把打包/更新/多平台适配当作 v0.2 目标 |
| 公网部署与 SaaS 化          | 涉及安全、运维与合规，当前只提供可选的自托管服务端                                |
| **插件市场（L2）**         | 分发与治理问题（审核/签名/沙箱/分成），依赖账号体系与多租户，远期再议              |

## 4. 用户与典型场景

### 4.1 目标用户

- **主要用户**：在校大学生（本科为主），有课程资料、需要备考/竞赛、习惯用电脑学习。
- **次要用户**：愿意参与共建的同学（开发者/设计），通过 PRD 与扩展性契约理解系统边界。

### 4.2 统一语言（术语表）

> 本节与代码中的类名、API 字段保持一致（DDD 的统一语言要求）。

| 术语   | 英文/代码             | 定义                           |
| ---- | ----------------- | ---------------------------- |
| 资料   | `Document`        | 用户导入的一份原始材料（一个文件或一段粘贴文本）     |
| 主题   | `Topic`           | 资料的**唯一归属**单位（如「计组」「密码学」）；同时是向量检索的**分区键** |
| 标签   | `Tag`             | 跨主题的**横向切面**（如「重点」「代码」「易错」）；一份资料可有多个 |
| 片段   | `Chunk`           | 资料切分后的最小检索单元，带来源定位与 `topic_id` |
| 知识库  | `KnowledgeBase`   | 某个空间内全部已索引资料的集合（每个空间一个，跨空间隔离）    |
| 笔记   | `Note`            | 用户可编辑的知识载体；分草稿 `draft` 与定稿 `confirmed` 两态 |
| 题目   | `Question`        | 由资料生成的检测题，含题干、题型、选项、答案、解析、来源 |
| 练习   | `PracticeSession` | 一次作答过程，包含若干题目与作答结果           |
| 错题   | `WrongAnswer`     | 作答错误（或自评未掌握）的题目记录            |
| 回顾报告 | `ReviewReport`    | 某时间窗内的知识总结 + 错题分析 + 复习建议     |

### 4.3 四个典型场景

**场景 A：期末前把课件变成可问答的知识库**  
小林有 12 份 PDF 课件，全部归入主题「计算机组成原理」，标上`重点`、`公式`。他问"第三章讲的三种排序算法复杂度分别是什么？"，系统给出答案并标注来源"第 3 章.pdf 第 12 页"。

**场景 B：用资料出题做自测**  
小陈复习完一章，直接选主题「密码学」出 10 道题（6 选择、2 判断、2 简答）——不必手动勾选 8 个 PDF。作答后客观题自动判分，简答题对照参考答案自评。错题自动进入错题本，并在错题本里按主题聚合成"密码学错得最多"。

**场景 C：边学边整理成自己的笔记**  
小周在学 langchain。他把官方文档和几篇教程导入主题「大模型应用开发」，打上`代码`标签。选这三份资料 +「代码笔记」模板，AI 生成草稿：每个知识点含原理、最小示例、常见坑，每条要点带来源角标。他一边看右侧原文一边改，删掉两段过时 API、把一段「AI 补写」换成自己跑通的代码，然后确认定稿。期末复习按主题筛笔记，比翻原始文档快得多。

**场景 D：周末收到学习回顾邮件**  
周日 9:00，小林的邮箱收到一封邮件：本周新增 3 份资料、完成 2 次练习、正确率 72%，按主题分组给出"计组投入最多、密码学正确率最低"，附"本周错题 TOP5 与薄弱知识点"，并给出下周复习建议。

## 5. 功能需求

> 每条需求包含：描述、规则/约束、验收标准（可客观验证）。  
> 编号规则：`FR-xx`。当前实现进度与阶段划分见 `docs/CLIENT_SERVER_SPLIT.md`。

### FR-01 资料导入

**描述**：用户可上传文件或直接粘贴文本，作为知识库的资料来源。

**规则**

1. 支持格式：`.pdf`、`.md`、`.txt`、`.docx`。
2. 单文件大小上限 20 MB；超出时拒绝并提示。
3. 粘贴文本：用户输入标题（可选，默认取首行）与正文，正文上限 100,000 字符。
4. 导入后文档进入"处理中"状态，处理完成变为"已完成"，失败变为"失败"并给出原因。
5. 同一文件重复上传允许（视为新资料），不做去重（v0.1）。
6. **必须选择主题**（单选，默认取上次使用的主题；无主题时归系统内置的「未分类」），可多选**标签**。批量导入时统一应用同一组主题与标签，事后再逐份调整。

**验收标准**

- [ ] 上传一份 5 MB 的 PDF，列表中出现该文档且状态最终为"已完成"。
- [ ] 上传 25 MB 文件，被拒绝并给出明确提示。
- [ ] 粘贴 500 字文本，生成一条资料并完成索引。
- [ ] 上传损坏的 PDF，状态为"失败"并展示错误原因。
- [ ] 上传时未选主题，自动归入「未分类」，可按该主题筛选到。

### FR-02 知识库索引

**描述**：将资料解析为纯文本，切分为片段并向量化，写入本地向量库。

**规则**

1. 解析：PDF 用文本抽取（非 OCR），DOCX 抽取段落，MD/TXT 直接读取。
2. 切分：按中文句读（。！？；\n）优先切分，目标 chunk 500~~1000 字符，重叠 100~~200 字符。
3. 每个 chunk 携带元数据：`document_id`、`chunk_index`、`source_name`、`page`（PDF 可获取时）、`topic_id`。
4. 向量化使用配置中的 Embedding Provider（默认本地 BGE-small-zh）。
5. 删除文档时，同步删除其全部 chunk 向量与元数据。
6. 切换 Embedding 模型后，**必须重建索引**；系统需检测模型变更并提示用户。
7. `topic_id` 作为向量表的 **partition key**。按主题检索时必须在分区内取 Top-K，**不得**全库召回后过滤（否则分区内容少时召回不足）。

**验收标准**

- [ ] 上传的 PDF 在向量库中产生 ≥1 个 chunk，且 chunk 数随文档长度增加。
- [ ] 文档列表展示：名称、主题、标签、类型、大小、chunk 数、状态、导入时间。
- [ ] 删除文档后，向量库中该 `document_id` 的 chunk 数为 0。
- [ ] 更改 Embedding 模型后再次提问，系统提示"索引需重建"。
- [ ] 主题 A 下只有 2 份资料时，限定主题 A 检索仍能返回这 2 份的片段（验证分区内取 K 而非全局过滤）。

### FR-03 问答与溯源

**描述**：用户用自然语言提问，系统基于知识库检索并生成答案，附来源。

**规则**

1. 检索：对问题做向量化，取 Top-K（默认 5）相关 chunk。
2. **检索范围**：默认全库；用户可限定为某个主题或某组标签。限定时走向量分区过滤（见 FR-02 规则 7），**不是**召回后再过滤。
3. 生成：将检索片段作为上下文交给 LLM，要求**仅依据上下文作答**。
4. 回答必须附**引用来源**：文档名 + 主题 + 命中片段摘要（可点击展开原文）。
5. 当检索结果的相关度低于阈值（默认 **0.42**）或无结果时，明确回答：**"知识库中没有找到相关资料"**，不得编造。
   阈值依据实测：bge-small-zh 下相关提问落在 0.55~0.76，无关提问 0.13~0.46，原来的 0.3 会把"如何用 pandas 读 excel"也放进来。
   0.42~0.55 属"擦边命中"，不直接拒答，而是在提示词里追加一段：先判断片段能否回答问题，答不了就只回一句没找到。
5.1 **未命中时的兜底作答**（`ANSWER_WITHOUT_CONTEXT`，默认开）：检索无结果时，
   先声明"没有找到相关资料"，再改用模型的**通用知识**作答。这条兜底回答：
   - 不绑定任何片段，也不得输出 `[n]` 角标（提示词禁止，界面也不给角标解析）；
   - 界面在回答**下方**渲染"以下内容由 AI 生成，未使用你的资料，请注意甄别"；
   - 允许进入多轮上下文（它是一轮完整对话），但不参与"存为笔记"（没有可回溯的来源）。
   两种情形**声明的位置不同**，因为"库是空的"属于页面状态，"这次没召回"属于这一轮对话：
   | 情形 | `reason` | 声明放在哪 | 是否作答 |
   |---|---|---|---|
   | 知识库一条片段都没有 | `empty` | 对话区**顶部状态条**，进页面显示一次，导入资料后自动消失 | 作答，底部标注"未使用你的资料" |
   | 有资料但本次没召回 | `no_match` | 该条回答**上方**的声明块 | 作答，底部标注"未使用你的资料" |

   空库不逐条重复，是因为同一句话在每条回答前再写一遍没有新信息，
   反而把每次回答都盖上一层"可能有问题"的底噪；页面级状态放在页面级位置更准确。
6. 对话支持多轮，保留最近 N 轮（默认 5）上下文；超出后滚动丢弃。
7. 知识库为空时**仍然允许提问**：对话区顶部显示一条状态条（"知识库中还没有资料 / 回答将由 AI 通用知识生成，
   不引用任何原文"，附"去导入资料"入口），提问照常作答，但**不再在每条回答前重复这段声明**。
   状态条在进入页面时自动显示，判据与后端一致（已入库片段数为 0）；切回窗口时重新查询，导入资料后自动消失。
   过去这里只提示导入、不生成回答，等于把产品最关键的一条路径锁死在"必须先有资料"上。
8. **AI 生成声明常显**：每段回答下方固定一行"本回答由 AI 生成，可能有误，请以下方引用原文为准"；
   若回答没有关联任何片段，声明改为"未关联任何资料片段"；若关联了片段但正文一个 `[n]` 都没标，
   声明改为"未标注引用，结论未与资料核对"。三种措辞对应三种可信度，不折叠进问号。
9. 检索未命中时区分两种情形并给不同出口：库为空 → 顶部状态条带"去导入资料"，底部的"可以这样问"示例
   同时换成不依赖资料的问法；有内容但都不相关 → 若当前限定在主题/标签内，给"不限范围再问一次"按钮，
   不带范围重发同一问题。

**验收标准**

- [ ] 针对已导入文档提问，答案正确且列出至少 1 条来源。
- [ ] 提问知识库完全无关的内容，回答"知识库中未找到相关内容"，不编造。
- [ ] 知识库为空时提问，给出引导提示。
- [ ] 点击来源可查看对应原文片段。
- [ ] 限定在主题「密码学」提问，来源列表中不出现其他主题的文档。

### FR-04 生成检测题

**描述**：基于知识库内容，由 LLM 生成带答案与解析的检测题。

**规则**

1. **题型**：选择题（单选/多选）、判断题、简答题。
2. **出题范围**（三种入口）：
   - 按主题：选 1 个或多个主题，自动包含其下全部已完成的资料（**默认入口**）。
   - 手动选定：勾选一个或多个文档（或全部）。
   - 按近期新增：自动取最近 N 天（默认 7 天）导入的资料。
   入口可叠加（如"主题=密码学 且 近 14 天"取交集）。
3. **可配置项**：题目总数（1~30，默认 10）、各题型数量或比例。
4. 每题必须包含：题干、题型、选项（选择/判断）、**正确答案**、**解析**、**来源**（文档名 + 片段）。
5. **防幻觉约束**：题目必须严格基于检索到的片段；若某范围资料不足以出题，返回"资料不足，无法出该题型"，不得凭空编题。
6. 生成结果先以"草稿"呈现，用户可删除个别题目后再开始作答。

**验收标准**

- [ ] 选择一个文档，生成 10 道题，题型分布符合配置。
- [ ] 每道题均含答案、解析、来源。
- [ ] 选择主题「密码学」出题，题目只来自该主题下的资料。
- [ ] 选择"近 7 天"入口，只包含 7 天内导入的资料。
- [ ] 对一段 50 字的资料要求生成 30 道题，系统提示资料不足而非强行编题。

### FR-06 错题沉淀

**描述**：打开 A4S 先看到自己的学习状态，而不是一个空白的功能列表。它是客户端的"个人主页"——数据来自当前空间，不跨空间汇总。

### FR-12 主题与标签体系

**描述**：用户用「主题」组织资料归属，用「标签」做横向切面。二者共同构成知识库的组织骨架，并作为问答、出题、错题、回顾四个模块的**范围参数**。

**规则**

1. **两层语义**（不可混用）：
   - **主题（`kind='topic'`）**：资料的**唯一归属**。每份资料必须且只能属于 1 个主题；未指定时归入系统内置的「未分类」（不可删除、不可改名）。
   - **标签（`kind='tag'`）**：**多值横向切面**。一份资料可挂 0~N 个标签。
2. **CRUD**：支持新建、重命名、设置颜色、排序、删除。名称在同类内全局唯一（不区分大小写），重名时提示而非静默合并。
3. **删除语义**：
   - 删除主题 → 其下资料**不删除**，自动迁移到「未分类」；chunk 的 `topic_id` 同步更新；资料数与 chunk 数不变。
   - 删除标签 → 仅解除与资料的关联，不影响资料与向量。
4. **预置包**：首次进入知识库且主题数为 0 时，引导用户选择 1~3 个学习方向，从 `backend/shared/seed/topic_packs.json` 批量创建主题与默认标签（内容见附录 B）。可跳过，跳过则只有「未分类」。
5. **批量操作**：支持对多份资料批量设置主题、批量增删标签。
6. **分区键**：每个 chunk 冗余存储 `topic_id`，作为向量表的 partition key（见 FR-02 规则 7）。主题改名不改变 id，因此不影响分区。
7. **在界面上的落位**：
   - 知识库左栏 = 主题列表（含各主题资料数），点击即筛选。
   - 顶部 = 标签筛选条（多选，取交集）。
   - 其余四页（问答/练习/错题/回顾）的范围选择器复用同一套主题/标签选择组件。

**验收标准**

- [ ] 新建主题「密码学」，上传一份 PDF 指定该主题，左栏按主题筛选可见。
- [ ] 一份资料不能同时属于两个主题（API 与 UI 均拒绝）。
- [ ] 删除「密码学」后，其下资料出现在「未分类」，资料数与 chunk 数不变。
- [ ] 重命名主题后资料归属不变，按新名检索仍命中。
- [ ] 零主题状态下进入知识库触发方向选择；选 2 个包后主题与默认标签就位。
- [ ] 批量给 5 份资料打「重点」标签，一次成功且列表即时反映。
- [ ] 标签筛选多选时取交集（如`重点`+`代码`只留同时具备两者的资料）。

### FR-13 电子笔记

**描述**：用户可手写笔记，也可让 LLM 从资料整理出结构化笔记草稿；草稿经人工编辑并确认后才成为定稿。**AI 产出是提案，不是知识。**

**规则**

1. **来源类型**（`source_type`）：`manual`（空白手写）、`document`（从 1 份/多份资料或整个主题生成）、`chat`（一次问答结论，FR-03 接入）、`wrong_answer`（错题，P1）。
2. **两阶段状态机**：
   - `draft`（草稿）→ `confirmed`（定稿）。
   - 草稿**不参与**出题范围选取、错题聚合与回顾统计；v0.1 笔记不进入向量索引，因此也不参与问答检索。
   - 定稿记录 `confirmed_at`。定稿后仍可编辑，一旦编辑状态退回 `draft` 并提示"已修改，需重新确认"。
3. **AI 起草必须选模板**，输出结构由模板固定（避免每次结构漂移，导致笔记之间无法对比）：
   - **章节摘要**：按原文小节平铺，每节 3~5 条要点
   - **概念卡**：每个概念含「定义 / 为什么重要 / 易错点 / 相关概念」
   - **代码笔记**：每个知识点含「原理 / 最小可运行示例 / 常见坑 / 相关 API」
   - **公式清单**：每条含「公式 / 符号含义 / 适用条件 / 推导要点」
4. **可溯源**：AI 起草的每条要点携带来源 `chunk_id`，渲染为角标 `[1]`，点击在右侧栏展开原文片段。无法溯源的段落标记为「AI 补写」，并在顶部提示条汇总条数。
5. **编辑器**：Markdown 双栏（左源码 / 右实时预览）。支持标题、列表、表格、代码块（语法高亮）、行内与块级公式（KaTeX）、引用块；提供工具栏快捷插入。
6. **重生成**：草稿可「重新整理」，沿用原范围与模板；用户手改的内容**会被覆盖**，必须先二次确认。
7. **组织**：笔记同样挂 1 个主题 + N 个标签，与资料共用同一套主题体系。
8. **列表与搜索**：按主题、标签、状态、更新时间筛选；支持标题与正文全文搜索（SQLite FTS5，中文按字切分）。
9. **删除**：删除笔记不影响来源资料。
10. **不做**（v0.1）：笔记回灌知识库、版本历史、多人协作、块级编辑器。

**验收标准**

- [ ] 空白新建笔记，写 Markdown，右侧正确渲染代码高亮与公式；保存后列表可见且状态为草稿。
- [ ] 选一份 PDF +「章节摘要」模板生成，草稿含 ≥3 个章节与要点，每条要点带来源角标。
- [ ] 点击来源角标，右侧展开对应原文片段。
- [ ] 点确认后状态变定稿且 `confirmed_at` 有值；再次编辑后状态退回草稿。
- [ ] 知识库只有 1 份资料、另有 1 份相关内容笔记时，问答检索结果不含笔记内容（验证笔记不污染检索）。
- [ ] 「重新整理」弹出覆盖提示；取消则内容一字不变。
- [ ] 按主题筛选笔记结果正确；搜索中文单字可命中。
- [ ] 删除来源资料后，笔记仍可打开，其来源角标显示"来源已删除"而非报错。

### FR-14 学习计划（Agent 编排，v0.2）

> 全项目唯一带「动作 → 观察 → 再决定」回路的模块。判据与边界见 `docs/AGENT_DECISION.md`。
> **它只回答「接下来做什么」，不生产内容、不判分、不改笔记。**

**规则**

1. **输入**：可选一句目标（≤200 字），如「这周想把分组密码搞明白」。不填也能生成。
2. **前置检查**：资料与练习记录都为 0 时**不生成计划**，只返回一句引导。没有数据的计划只能是编造。
3. **循环上限**：最多 6 步，每步一个工具调用；同一只读工具最多调 2 次，第三次直接回「已经查过了」。
4. **工具集（5 个）**：`get_progress`（进度）、`list_weak_points`（薄弱点）、
   `list_wrong_answers`（错题原文）、`generate_practice`（复用出题器，不自写题）、`save_plan`（唯一写操作）。
5. **写边界**：只有 `save_plan` 写 `study_plans` 一张表；不改笔记、不改错题本、不改题库。
6. **数值边界**：计划里的每个数字必须原样来自工具返回，不许估算、不许做运算造新数字。
7. **计划结构**：按天给出「做什么 + 做到什么程度算完成」，粒度 7 天；不做月度/季度规划。
8. **一次会话一份计划**：无跨会话记忆，每次从数据库重新读；不在后台常驻，关页面即停。
9. **失败出口**：步数用尽或模型报错时，只返回已查到的结论 + 一句说明，**不产出半张计划**。
10. **可溯源**：每步的工具名、入参、是否成功、结果摘要写入 `study_plans.meta.steps`，界面可展开查看。
11. **不做**（v0.2）：日历排期、提醒推送、计划执行打卡、多计划对比。

**验收标准**

- [ ] 空库点「生成计划」→ 只出现引导文案，`study_plans` 不新增记录。
- [ ] 有错题时生成的计划，提到的薄弱点名称与错题本按主题聚合的结果一致。
- [ ] 计划正文里出现的每个数字，都能在步骤时间线的某一步返回值里找到同值。

## 6. 技术约束与关键决策

### 6.1 技术栈

| 层         | 选型                                | 理由                                    |
| --------- | --------------------------------- | ------------------------------------- |
| 前端        | React 18 + Vite 6 + TypeScript     | 生态成熟、共建资源丰富、组件库多                      |
| 后端        | Python 3.11+ / FastAPI            | RAG/文档解析生态最成熟，异步好，自动生成 OpenAPI        |
| 入库与检索     | 自研解析 → 切分 → FTS5 + sqlite-vec 双路召回 | 不引入重型索引框架：切分与过滤规则都在这一个项目里，少一层黑盒；混合召回先向量后文本重排，可单独测 |
| Agent 编排  | v0.2 仅学习计划用轻量工具循环（`plan_agent`），不引入 LangGraph | 只有「下一步做什么」需要模型判断；图编排对当前 5 个工具是过度设计（见 `docs/AGENT_DECISION.md`） |
| 向量库       | sqlite-vec（SQLite 扩展）              | 预编译 wheel 无编译、与关系库同文件、元数据过滤用 SQL、未来可切 pgvector |
| Embedding | 本地 BGE-small-zh（默认），云端可切          | 零成本/离线/中文好；规避 DeepSeek 无 embedding 接口 |
| LLM       | OpenAI 兼容协议统一适配                   | 一套 SDK + base_url 接多家                 |
| 关系库       | SQLite + SQLAlchemy ORM + Alembic | 零配置；ORM 隔离使未来可平滑切 PostgreSQL          |
| 定时/邮件     | APScheduler + smtplib/email       | 轻量够用                                  |
| 笔记渲染      | react-markdown + remark-gfm + KaTeX + highlight | LLM 原生输出 Markdown，零转换损失；公式与代码块是刚需；比 Tiptap 少 1.5 天工作量且无格式往返失真 |
| 全文搜索      | SQLite FTS5（中文按字切分）              | 零依赖；中文无词边界，`unicode61` 分词器对中文按字切分即可满足笔记搜索 |
| 桌面外壳      | Tauri 2（可选）                      | 复用同一套前端；不改变 WebUI 主形态 |

### 6.2 架构约束

1. **分层依赖向内**：`api → services → domain`，`domain` 不依赖任何框架与 IO；`infrastructure` 只被外层装配调用。
2. **两端边界（v0.2）**：`shared` 不依赖 `client` 或 `server`；`client` 不依赖 `server`，服务端离线时客户端功能不降级。可用 `grep` 自动校验（见 CLIENT_SERVER_SPLIT §3.2）。
3. **数据库可迁移**：全部数据访问经 SQLAlchemy ORM；`DATABASE_URL` 配置化。不写裸 SQL。
4. **模型供应商可替换**：LLM/Embedding 均通过 Provider 接口，配置驱动切换。
5. **框架隔离**：解析器、向量库、LLM SDK 等外部实现的细节不得泄漏到 `domain` 与 `services` 的对外签名中。
6. **能力集中装配**：可替换能力（LLM / Embedding / 解析器 / 出题器 / 通知器）由各自的工厂函数构造，业务代码不直接 `import` 具体实现类，只调用工厂。

| ADR-15 | 客户端 / 服务端**物理拆分**：`shared` 共用领域与内容栈，`client` 持有个人学习功能，`server` 只持身份、关系与公共库 | 前端只连客户端，本地有就答、需要远端再转发；服务端离线时界面显示离线而不是超时；个人资料永不上传 | 继续单体：两个进程写同一个 SQLite 文件会锁冲突，且无法把"公共服务"独立部署 |
| ADR-16 | 响应式与大屏适配写入界面契约：断点 1180/900/720/600/460，≤900 侧栏转顶部导航，≥1600 内容区与字号分档放大 | 同一套界面要能覆盖笔记本、平板与大屏；只做"能挤下"会在 27 寸屏上出现一条窄内容挂在中间 | 固定 1200px 居中：大屏浪费、小屏横向溢出；做两套 DOM：维护成本翻倍 |

## 7. 扩展性契约（L0）

> **本节是贡献者契约**：新增能力必须通过既有接口 + 工厂函数装配，不得修改内核调用链。

| 扩展点                 | 接口职责                                               | v0.1 内置实现                 | 未来可接             |
| ------------------- | -------------------------------------------------- | ------------------------- | ---------------- |
| `LLMProvider`       | `chat(messages, **opts) -> str`、`stream(...)`      | DeepSeek / 通义 / OpenAI 兼容 | 本地模型、新供应商        |
| `EmbeddingProvider` | `embed(texts) -> list[list[float]]`、`dimension`    | 本地 BGE-small-zh、云端 API    | 其他嵌入模型           |
| `DocumentParser`    | `supports(ext) -> bool`、`parse(path) -> ParsedDoc` | PDF / MD / TXT / DOCX     | PPT、Excel、网页、OCR |
| `QuestionGenerator` | `generate(context, config) -> list[Question]`      | 选择 / 判断 / 简答              | 填空、计算、编程题        |
| `Notifier`          | `send(report) -> Result`                           | 邮件（SMTP）                  | 微信、系统通知、日历       |

**装配与切换**：每个能力有一个工厂函数（`build_llm` / `build_embedding` / `resolve_parser` /
`LLMTypedGenerator` / `build_notifier`），配置项决定走哪个分支；业务代码只调工厂，不 import 具体类。
新增一种实现，只改工厂内部的那个 `if` 或字典。

> 本节原为「扩展点契约」，要求所有能力经 `registry.py` 注册。v0.1 收尾时取消了注册表
> （理由见 ADR-08），接口约定保留，装配方式改为工厂函数。`ReviewRenderer` 一项目前无实现，已从表中移除。

**演进路线**

- **L0（v0.1，本期）**：内部扩展点，无外部加载。
- **L1（v0.5 可选）**：`plugin.toml` 清单 + 入口点 + 目录扫描，支持安装第三方插件，但无分发与审核。
- **L2（v1.x 远期）**：插件市场，需账号体系、上传审核、版本依赖、签名、沙箱权限、收益分成。**v0.1 不设计**。

**每个包附带默认标签（`kind='tag'`）**：`重点`、`公式`、`代码`、`易错`、`待整理`。

**设计说明**
1. 主题名是**具体的课程/技术名**而非宽泛门类（不写"计算机"，写"计算机组成原理"），因为学生的检索提问天然带课程名；包本身只是批量创建的模板，创建后完全可改。
2. 主题名在同一用户的主题空间内**全局唯一**，因此跨包不得重名（如「离散数学」只放在 `math` 包，`cs-core` 不放）。导入预置包时按名称幂等：已存在的主题跳过而非报错。
3. 共 9 个包、57 个主题、5 个默认标签。
